# 第2回OC：学生スタッフ用 統合実機確認手順（PR #21レビュー案）

この一文書で現状記録、指定版の確認、ビルド、車輪浮上試験、報告まで進めるための案です。PR #20の準備ガイダンスとPR #21の旧補足を統合しました。PR #20のブランチ自体は変更していません。教員が承認したら、本書を学生配布の正本とし、PR #20側の旧説明は重複配布しない方針を提案します。

**機体ボタンは実装候補であり、実機合格済みではありません。** 担当教員は遠隔で判断します。分からなければ操作を止めて記録・報告してください。実機SDKビルドと機体試験は学生が後日、教員の具体的許可後に行います。

## 0. 担当・承認・準備

- 学生スタッフは現地の確認と記録、開発担当は実装とホストテスト、担当教員は実機許可・次段階判断を担当します。
- 初回は必ず2名。操作担当と、機体・周囲・物理停止を担当する監視担当を決めます。車輪を床・机に触れない安定した台で浮かせます。
- SPIKE Primeの電源を含む物理停止方法と、すぐ手が届くことを確認します。フォースセンサーはソフトウェア入力であり、OS/Hub/USB/ハード故障時の確実な停止手段ではありません。
- 作業前に教員へ機体番号、担当者、日時、PCを連絡し、下表を埋めます。許可がない段階は実施しません。

ネットワークが切れてもプログラムを自動停止する仕様ではありません。切断中のWeb終了に頼らず現地停止を担当します。ネットワークやOS設定、sudoers、systemdを独断で変更しないでください。

git remote -v

git -C ~/RasPike-ART rev-parse HEAD

git -C ~/RasPike-ART submodule status --recursive

## 2. 教員指定の実装版を準備・照合する

教員が差分保存と切替を承認してから指定した作業領域/コミットへ切り替えます。切替方法は現地の未保存変更に応じて教員が指定します。変更を消して切り替えたり、mainをその場で編集したりしません。切替後に記録します。

```bash
cd ~/raspike-spike-demo
git rev-parse HEAD
git status -sb
git diff -- robot/ocan2026
```

教員指定SHAと一致しなければビルドへ進みません。実装候補では以下を確認します。

| ファイル/実機 | 確認事項 |
| --- | --- |
| app.c | tracer_taskが学習領域。main_taskが初期化後も継続監視する |
| LineTracer/RobotControl.c | 解放後の新押下、チャタリング、開始/一時停止/再開、停止時の予約取消し |
| LineTracer/LineTracer.c | 学習APIは指令を渡すだけ。実出力は固定監視側。停止中の指令は捨てる |
| app.h / app.cfg / Makefile.inc | main優先度が学習より高い。RobotControl.o登録がある |
| 機体のポート | 左モーターB、右A、カラーE、フォースD。実機と一致しなければ中止 |

## 3. ビルド・車輪浮上での初回起動（明示許可後）

1. 既存のロボット実行を教員指定の管理経路で終了し、車輪停止・機体占有を確認します。Web/CLIを混用して二重起動しません。
2. 低速設定はスタッフが教員の指定値だけを変更し、差分を記録します。旋回用は `0 <= TURN_SPEED < BASE_SPEED <= 100` とします。単にBASE_SPEEDだけを下げて内外差を反転させないでください。
3. 学習命令をまず `forward();` のみにします。`tracer_task()`内の `(void)unused;` と `ext_tsk();` を残し、その間のif/else部分を置き換えます。固定監視側やSDKは編集しません。
4. Pi側リポジトリで名前指定ビルドを行い、終了コードと全ログを保存します。

```bash
cd ~/raspike-spike-demo
scripts/build-robot ocan2026
```

失敗したら実行しません。aspの存在は成功の証拠ではありません。現地SDK版やツールチェーンが変わった場合は、既存cacheのhitだけで新SDKでのビルド成功とみなさず、教員がcache再生成の方法を指定します。学生がSDK/cacheを独断で削除しないでください。

5. 教員が成功ログを確認し実行を許可したら、次のどちらか一経路で起動します。
   - CLI: `scripts/start-robot ocan2026`（対象を再確認・ビルド/cache後に起動）。ターミナルを監視します。
   - Web: 既存ダッシュボードのocan2026カードから実行。CLIと併用しません。
6. `[ocan2026] WAITING`と車輪停止を確認します。ERROR、初期化停止、想定しないプログラムなら即中止。ログのrunningやプロセス生存だけで走行/停止を判定しません。

## 4. ボタン・停止保持・単独命令試験

すべて車輪浮上・2名で実施します。各操作前後のログと車輪を記録します。

| 順番 | 操作 | 期待結果 |
| --- | --- | --- |
| 1 | 起動後、押さずに観測 | WAITING、車輪停止 |
| 2 | 一回押して解放 | RUNNING、前進向きに回転 |
| 3 | 再度押して解放 | PAUSED、車輪停止。指定観測時間中に再駆動しない |
| 4 | 再度押して解放 | RUNNING。古い途中処理でなく次の学習周期から再開 |
| 5 | 走行中・停止中に長押し | 一押下で一切替。保持中に反復しない |
| 6 | 短い押下/解放、連打 | チャタリングで余計に反転しない。短すぎる入力は無視され得るため回数どおり切替は要求しない |
| 7 | 機体を停止・実行終了後、押しっぱなしで再起動 | 走らない。安定解放後の新しい押下でのみ開始 |

通常10ms間隔で同じ入力4回を確認します。約30～40msは入力判定の目安で、実際の停止時間の保証ではありません。押下から車輪停止までの時間、惰性回転も記録します。ゼロPWMはブレーキ/位置保持の保証ではありません。

続いて実行終了・停止を確認してから、学習命令を `left();`、次に `right();`、最後に `stop();` に一つずつ置換し、その都度再ビルドして同じ待機/ボタン試験を行います。black/whiteを先に呼ぶ必要はありません。

| 命令 | 実装上の左右PWM（初期定数時） | 実機の確認 |
| --- | --- | --- |
| forward | BASE_SPEED / BASE_SPEED（50 / 50） | 同じ前進方向 |
| left | TURN_SPEED / BASE_SPEED（5 / 50） | 左車輪が遅い。実際に左旋回するか床面は別承認後 |
| right | BASE_SPEED / TURN_SPEED（50 / 5） | 右車輪が遅い。実際に右旋回するか床面は別承認後 |
| stop | 0 / 0 | RUNNING状態でも回らない |

講師設定を変えたら表の数値を実値へ読み替えます。旧実装はsteering初期値0でleft/rightが50/50になり、センサー判定後はその値に依存しました。今回その履歴依存を取り除いています。比例旋回から固定内外差へ変わるため、既存if課題のコース追従性も後日確認が必要です。

## 5. 通信断・実行終了と復帰

1. 車輪浮上でforwardの通常試験を済ませてから、PC側のWi-Fi接続を一時的に切る/ブラウザを閉じます。Piのネットワーク設定は変更しません。
2. それだけでは停止せずPi内プログラムが継続すること、現地ボタンで一時停止・再開できることを確認します。常に監視担当が機体横に付きます。
3. 同じ機体へ再接続し、現在状態を取得します。実行や走行再開を自動で要求せず、二重に起動しません。現行Webの表示はプロセス状態が中心なので、車輪とログも確認します。
4. Web起動ならカードの停止、CLI起動なら同じターミナルのCtrl+Cで実行終了します。接続断中のWeb終了には頼りません。プロセス終了と車輪停止を別々に記録します。
5. 終了しない/状態不明なら重ねて起動せず、物理停止で安全を確保し教員へ報告します。

PCの映像フリーズはPi内部画像処理停止と同じではありません。内部画像/指令更新停止・Python–C断での安全停止は別要件として維持しますが、カメラなしocan2026のこの試験ではその検証を行いません。

## 6. 中止条件・異常コード・床面走行

ボタンで止まらない、停止後に勝手に再駆動、誤バイナリ、ERROR、発熱/電圧低下/異音、固定具不安定なら即中止します。必要なら物理停止し、教員が原因確認するまで再走行しません。ERRORは停止要求の記録であり、物理停止済みの証明ではありません。

無限ループ、長いdly_tsk、forward等の繰返しによる試験は、通常試験合格後に教員が指定コード・手順・中止条件を別途承認した場合だけ行います。学生が独自に割込み禁止、USB抜去、OS停止等を試さないでください。観測点は「学習処理が戻らなくても監視に戻れるか」「ボタン停止が効くか」「再駆動しないか」「再開が古い途中処理を再生しないか」です。

車輪浮上の結果を教員に報告し、追加承認後に低速・安全コースで前進/左右旋回・if課題を確認します。床面走行は別判断です。実機停止が未確認なら床面走行しません。ソフトの監視は任意Cの直接モーターAPI、割込み禁止、優先度変更、メモリ破壊、OS/ハード故障を隔離する機能ではありません。

## 7. 終了・復旧・交代

終了と車輪停止を確認してログ・差分・動画を保存します。テスト用本文/低速設定の差分を教員へ渡し、指定された方法で元へ戻します。git reset --hard等で未知の変更を消さず、ブランチを戻すだけでaspが戻るとも考えません。必要なら戻し先ソースで再ビルドします。

本PRにはWeb編集やスタッフRestoreボタンは実装されていません。将来の交代手順は実行終了・停止確認→スタッフRestore→必要なら再ビルドで、自動走行させません。今回は教員指定の手動復旧を使います。故障時は検証済みデモや、有線/HDMI＋ローカル入出力へ退避するかを教員が判断します。

## 付録A. SDK初期状態の確認結果（開発担当・教員向け）

静的参照版は `ETrobocon/RasPike-ART` の `7bfc34b81b3df5acdc6060ba9e72ae33134d492d`、submodule `libraspike-art` の `86b610c105206bb9df5ae694f7d11e2d16e0e3d2`。採用予定SDKの照合基準とし、現地の版が一致/同等かは§1で確認します。採用版の現物はCodex側にありません。

app.cfgは周期をTA_NULL、学習タスクをTA_NULL（自動開始なし）、mainだけTA_ACTと定義しています。mainの初期化時は周期未開始・学習タスク休止です。

| APIと参照実装 | 初期状態の処理・戻り値 | stop_learningの扱い |
| --- | --- | --- |
| [stp_cyc / kernel/cyclic.c](https://github.com/ETrobocon/RasPike-ART/blob/7bfc34b81b3df5acdc6060ba9e72ae33134d492d/kernel/cyclic.c) | 定義済み周期ならcycstaがfalseでもE_OK。trueの時だけイベントを取り除く | E_OKのみ正常 |
| [can_act / kernel/task_manage.c](https://github.com/ETrobocon/RasPike-ART/blob/7bfc34b81b3df5acdc6060ba9e72ae33134d492d/kernel/task_manage.c) | 休止状態をエラー判定せず、actqueがfalseなら0。trueなら1を返して予約を消す | 0以上を正常 |
| [ter_tsk / kernel/task_term.c](https://github.com/ETrobocon/RasPike-ART/blob/7bfc34b81b3df5acdc6060ba9e72ae33134d492d/kernel/task_term.c) | 他タスクが休止ならE_OBJ。起動中/待ち中なら終了してE_OK | E_OKまたはE_OBJのみ正常 |

従って初期状態のE_OK/0/E_OBJは現実装で正常終了し、停止判定の動作修正は不要です。この契約と、stp_cyc/can_actのE_OBJを誤って正常扱いしない回帰テストを追加しました。未定義E_NOEXS、不正ID、CPUロック/不正コンテキスト等のエラーを正常扱いへ広げていません。mainは有効ID・CPUロック解除・別学習タスクIDで呼ぶ前提です。

周期停止→can_act→ter_tskの順は維持します。終了前に予約起動を消し、終了に伴う予約再起動を避けます。API/出力失敗はfaultに固定し、スタッフが終了・原因確認します。

## 付録B. 静的検証の限界と後続教材課題

公開SDKのSIGALRM/シグナルによる切替、ter_tsk/can_actを調査しました。モーターset_powerはACK待ちなしですが、下層の送信mutex/writeは待ち得ます。forceは保存状態を読むため、Hub/USB通信が止まると値が古いままになり得ます。学習タスクの正常終了を待たない構成でも、実際のプリエンプション/停止時間は実機未検証です。

ホストテストは実装Cをスタブとともにコンパイルして、ボタン、出力抑止、初期戻り値、単独left/rightと判定履歴非依存を検査します。SDKカーネルを動かす試験ではありません。実機SDKのcfg生成/リンク/aspビルド、スケジューラ、惰性、物理停止は後日学生が確認します。

**後続教材課題:** smooth_traceは今回も宣言だけで実装はコメントアウトのままです。呼び出す課題/完成例は配布・試験しません。別PRで実装するか課題から外すかを決め、STEERING_COEFの説明、README、PowerPoint、完成ファイルを同時に整合させ、ビルドとコース試験を行います。今回のleft/rightは固定PWM差のON/OFF旋回で、比例制御ではありません。
