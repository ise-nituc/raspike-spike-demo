# 機体ボタン実装：実機確認の補足・PR #20への修正案

Issue [#19](https://github.com/ise-nituc/raspike-spike-demo/issues/19)の実装候補に対する補足。学生向けガイダンス[Draft PR #20](https://github.com/ise-nituc/raspike-spike-demo/pull/20)自体は変更せず、以下を追加・置換する案とする。mainへマージ済み／実機合格とは扱わない。

## 実装の要点と静的調査

- `main_task`は`TMIN_APP_TPRI+1`、学習`tracer_task`は`+2`。既存の優先順位を維持し、mainが10,000µs待ちを挟んでボタンを継続監視する。
- ボタンは同じ値を4回連続で観測して確定する。通常10ms間隔なら最初の観測から約30ms以上、物理エッジから約30～40ms以上が目安。APIやスケジューラの遅れを含む停止時間の保証値ではない。起動時は押下済み扱いにして、安定した解放後の新押下を必要とする。
- `forward/left/right/stop`はCPUロック内の短いメモリ更新だけを行う。mainだけが実モーターAPIを呼ぶため、停止判定後に学習タスクが出力する競合を避ける。PWM±100制限とポートB/A/E/Dを維持する。
- mainが停止ゲートを閉じてゼロ出力し、周期起動を止め、残った起動要求を`can_act`で除去してから学習タスクを`ter_tsk`する（終了時の予約再起動を防ぐ）。再開は古い処理の続きでなく、次周期の先頭から。学習コードのstatic/global変数やセンサー判定の内部状態を初期化するRestoreではない。
- 保存された指令はmainが次に動く時に反映する。同じ学習処理中の複数命令は最後の指令が残るため、`forward(); stop();`で一瞬動かす用途には使わない。通常の一周期一命令の教材を想定する。
- API失敗時はERRORを記録し停止側に固定する。ボタンで復帰せず、スタッフが実行終了・原因確認する。

静的参照は公開SDK `ETrobocon/RasPike-ART` のコミット`7bfc34b81b3df5acdc6060ba9e72ae33134d492d`と、そのsubmodule `libraspike-art` の`86b610c105206bb9df5ae694f7d11e2d16e0e3d2`。現地SDKが同じとは仮定しない。

| 参照元 | 確認できた性質と限界 |
| --- | --- |
| SDK `target/raspi_gcc/target_timer.c`、`target_kernel_impl.c` | setitimer/SIGALRMとシグナルによるタスク切替がある。割込み・ディスパッチが有効なら高優先度監視へ戻る構成だが、実時間の遅延・無限ループ中の動作は未検証 |
| SDK `kernel/task_term.c`、`kernel/task_manage.c` | `ter_tsk`は他タスクを終了、休止ならE_OBJ。`can_act`は起動要求を取り消す。採用SDKの設定/生成物で利用可能か要ビルド確認 |
| lib `src/raspike_motor.c` | set_powerはACKを待たず、stop/brakeはACK待ち。従来と同じset_power(0)を使う。ただしset_powerの成功は送信・物理停止の確認ではない |
| lib `src/raspike_protocol.c`、`raspike_com.c` | 送信処理はmutexやwriteを含み、ブロックしない保証はない。SDK API内・USB不調時に監視が遅れる可能性がある |
| lib `src/raspike_forcesensor.c`、`raspike_internal.h` | touchedはPi側に保存された状態を読む。機体との通信断で値が古いままになる場合、ソフトのボタンだけでは止められない |

このゲートは教材APIを通る出力を対象とする。学習コードが直接pup_motor_*、制御用API、CPUロック/割込み禁止、優先度変更、メモリ破壊等を行う場合の隔離ではない。OS/Hub/ハード停止も含め無条件の停止保証はしない。他デモの内部TCP/画像鮮度監視は今回変更していない。PC・ブラウザ断を条件にするHeartbeatも追加していない。

## §3の通常試験に追加する手順（教員承認後・初回は2名・車輪浮上）

1. 教員が指定した実装PR/commitと機体SDK/submodule版を記録する。未保存編集は消さず退避し、戻し先も教員と確認する。
2. 教員指定の方法で`ocan2026`を名前指定ビルドする。ビルド成功ログと対象版を保存し、失敗したら実行しない。旧aspを代わりに使わない。
3. 起動後に`[ocan2026] WAITING`と車輪停止を確認する。初期化エラーなら以後の試験を中止する。
4. 一度押して`RUNNING`、二度目で`PAUSED`、三度目で`RUNNING`を確認する。押すごとに一度解放する。停止中は数周期以上観測して再駆動しないことを動画で確認する。
5. 起動時押しっぱなし、長押し、短い解放/押下、連打を分けて確認する。起動時押下は無視され、解放後の新押下で開始する。短すぎる操作は無視され得るので「連打回数どおり切替」を合格条件にしない。
6. Wi-Fi断/ブラウザ終了だけでは正常な走行が止まらないこと、その間も機体ボタンで停止・再開できることを車輪浮上で確認する。通信復帰でプログラムが自動再起動しないことも確認する。
7. Webの実行終了、または教員指定CLI終了を確認する。プロセス終了と車輪停止を別に記録する。このPRは既存Web/systemd終了処理を変更しない。
8. ゼロ指令はブレーキ/保持の保証ではない。押下から車輪停止までの遅延・惰性回転を測り、床面走行は別途教員が判定する。

## 異常コード試験は別承認・別の指定コードで行う

通常試験合格後、教員が具体的な手順と中止条件を指示した場合に限る。学生が独自に危険なコードを作らない。

| 指定試験 | 確認事項 |
| --- | --- |
| 学習処理内のCPU無限ループ（割込み禁止なし） | 走行中ボタンで停止できるか、監視が継続するか。停止後に再駆動しないか |
| 長いdly_tsk待ち | 待ち途中で停止し、再開後に古い処理の続きを実行しないか |
| forward等を繰り返す処理 | 指令発行が続いても停止ゲートが優先されるか |
| エラー/停止・終了時 | 物理停止方法がすぐ使えるか。ERROR後にボタンだけで走らないか |

OS/USB/Hub不調や割込み禁止はこの実装だけで停止できるとは限らない。機体ボタンが効かなければ指定した物理停止手段を使い、以後の走行を中止して教員へ報告する。承認なしにUSB抜去・OS停止等の故障注入はしない。

## Codex側での検証と未実施項目

`bash robot/ocan2026/tests/run-host-tests.sh`は実装CをSDK/モーターのテスト用スタブでコンパイルして実行する。起動時押下、4連続サンプルの境界、押下/解放チャタリング、長押し、開始/一時停止/再開、指令破棄、出力抑止、PWM制限、APIエラー固定を検証する。これは実機スケジューラ、生成cfg、USB/モーター動作の試験ではない。

Codex環境はx86_64で採用実機SDK/クロスコンパイラを備えていないため、実機用aspのビルド・リンク・cfg生成と実機試験は未実施。公開SDKは静的参照のみ。本番前に学生が教員の許可後に確認する。
