# 段階的な移行計画と第2回の最小実装

本PRは調査・設計のDraft。今回変更するのはarchitecture/の設計文書だけで、実装、既存README、systemd、sudoers、ネットワークの変更、実機操作は行わない。以下はレビュー後の別実装PRの計画。

第2回はスタッフのマンツーマン監督、通常Cによるtracer_task()本文編集、機体ボタンの開始/一時停止/再開、機体AP優先、スタッフ専用Restoreを採用する。ブラウザ断では走行を自動停止させず、Heartbeat/lease失効を停止条件にしない。Pi内部の画像・指令更新停止やPython–C制御通信断での安全停止とは明確に分離する。

## 1. 第2回に向けた最小実装の作業順序

| --- | --- | --- | --- | --- |

## 4. 受入試験

| ケース | 測定・確認 | 合格条件 |
| --- | --- | --- |
| Web実行・再実行・Pi起動 | モーター出力、待機状態、ボタン入力 | Web実行では走らない。起動時押下を持ち越さず、新しい押下で開始 |
| ボタン切替 | 押下/解放時間、長押し、チャタリング、連打 | 一押下一切替、走行→停止→再開。停止中の遅延指令を再生しない |
| 無限ループ・長い待ち・制御異常 | 監視タスクの実行、ボタンから車輪停止までの時間/距離 | 本文の正常終了やPC接続に依存して停止しない。SDK上の制約と対応を記録 |
| Web実行終了・強制終了 | モーター停止、プロセス/子プロセス残留 | ボタン一時停止と区別してプログラム終了。プロセスが消えただけで合格にしない |
| Wi-Fi断・タブ閉じ・ブラウザ映像フリーズ | 実行プロセス、ローカル制御、機体ボタン | PC側の断線/映像停止を停止条件にしない。ローカル制御が正常なら継続し、必要時ボタン停止できる |
| ブラウザ再接続・Web再起動 | revision、job結果、待機/走行/一時停止/終了の現在状態 | 状態取得のみ。プログラム再起動や走行再開要求の自動送信なし |
| Pi内画像更新停止・指令更新停止・Python–C断/無応答 | 内部の更新時刻/受信期限と停止時間 | 対象カメラデモの安全停止を維持。不足なら別PRで修正。ブラウザHeartbeatを代用しない |
| 通常C・構文エラー・本文逸脱 | 保存版、固定部分/他ファイル差分、コンパイラログ | 通常Cを独自限定文法で拒否しない。本文外への逸脱は防ぐ。構文エラー原文表示 |
| 失敗ビルド・保存競合・多重実行 | revision/asp対応、ロック、409、二重要求 | 古いaspを起動しない。想定外の遅延起動なし |
| スタッフRestore | 終了確認、初期本文、新revision、main差分 | 実行終了→復元、旧成果物無効、自動起動/走行なし。権限のない要求は拒否 |
| 多台数AP・有線・HDMI代替 | 接続時間、切断率、回復時間、機体取り違え、40分進行 | 予定台数で機体を識別でき、切断中の現地停止と代替操作が可能 |
| OS/ハード停止想定 | スタッフが使う物理停止方法と到達性 | ソフトウェアボタンに頼らず停止できる方法を実機で確認し手順化 |

停止距離・許容時間、監視周期・チャタリング時間は速度とコース余裕に基づき実測して決める。機体ボタンが一般のCのあらゆるOS操作・ハード故障を止めるとは保証しない。想定した通常コード不具合でも止められなければ、編集結果の走行を本番に導入しない。

## 5. 残る設計判断とレビュー範囲

先に決めるのはSDK上のボタン監視優先度・出力ゲート・異常時中断/再開、物理停止方法と停止距離。続いて通常Cと両立する本文境界検査、SDK実行の最小権限、スタッフ権限の渡し方とRestore終了確認、初期テンプレート、AP試験の判定値を確定する。

本Draftはこれらの設計レビュー待ちである。今回の更新を実装開始、sudoers/ネットワーク変更、実機操作、mainマージの承認と解釈しない。
