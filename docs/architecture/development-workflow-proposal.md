# 推奨する開発・実行方式

これは未実装の設計提案。[現状](current-state.md)と[不整合](inconsistencies.md)を前提とする。今回のPRは文書追加のみ。

## 1. 一つに絞った推奨構成

**正本は各Git checkoutの`robot/`、SDK workspaceは共通のビルド・実行領域、Web/CLIは同じ管理入口を使う。通常開発はRemote SSH、短時間体験は範囲と文法を限定したWeb編集、展示は選択・実行・停止の既存ダッシュボードを使う。**

SDKを置き換えず、既存のmake img、キャッシュ、flock、systemdを活かす。新しい汎用クラウドIDE、コンテナ群、分散ジョブ基盤は導入しない。Web体験に必要な保存・ジョブ管理と小さなローカル実行管理境界だけを追加する。

リポジトリ外を参照するmake img経路は既に実装されており、robot/を正本にすることを妨げる制約は確認できない。ただしSDKが外部ソースの全モジュールを正しく追跡すること、workspace/appdirの型、HOME固定パス、共通asp一つによる直列化、SDK版依存の起動権限は確認が必要。SDK workspace内のソース編集・コピー・リンクを通常手順に戻す理由にはならない。

## 2. 利用者と作業領域

| 場面 | 編集・保存場所 | 操作 | Gitと復元 |
| --- | --- | --- | --- |
| A 通常開発 | Pi上の学生用checkoutのrobot/。一台一組・一つの選択されたcheckout | VS Code Remote SSHを標準、nanoは代替。名前指定ビルド/実行、共通管理入口で停止 | studentブランチ、commit→bundle→PCでverify。mainは配布版 |
| B 40分体験 | 教員が準備した体験専用cloneのrobot/ocan2026/app.c | Webでtracer_task本文の許可文法だけ編集→保存→ビルド→実行→停止 | main上では編集しない。ocan/sessionブランチ。初期/完成テンプレートを復元 |
| C 展示 | 教員が確定した配布checkout。Webから編集しない | 既存カードの選択、開始、停止、状態・ログ | 固定したcommitと成果物ID。開始前にキャッシュを準備 |

同じ機体でA/B/Cを同時使用しない。教員がモードを選び、停止確認後に対象checkoutを切り替える。cloneを無制限に増やさず、通常の開発用と体験/展示用を区別するだけでよい。各checkout内のrobot/がその作業の唯一の編集元であり、SDKへのソース複製は正本にしない。

体験cloneは配布元から教員が作成し、Web利用ユーザーへGitHub書込み資格情報を渡さない。ブランチ名だけではmainへの保存や誤pushを防げないので、Web APIにはGit操作を公開せず、配布checkoutをWebから書けなくする。教材テンプレート・SDK・スクリプト・Makefile・unitは教員所有の読取り専用とする。提出内容は教員が差分を確認して通常PRに取り込む。自動マージや自動pushはしない。

## 3. 各処理の責任

| 処理 | 責任を持つコンポーネント | 成功条件 |
| --- | --- | --- |
| 編集 | 通常はエディタ、体験は制限Web UI | 許可された作業領域・編集範囲のみ |
| 保存 | Pi上の保存API | 構文/文法確認、版照合、一時ファイル→rename、保存revision応答 |
| ビルド | 非特権build workerと既存build機構 | 固定入力snapshot、終了コード、ログ、成果物とsource/SDK/toolchainの識別 |
| 実行 | ローカル実行管理＋systemd | 指定revisionの成果物のみ、機体全体で単独、既定停止状態から明示開始 |
| 停止 | 実行管理・独立安全監視・実機停止手段 | 子プロセス停止だけでなくモーター停止を確認。停止未確認はエラー |
| 復元 | 保存API（教員が配布したテンプレート） | 停止→現版退避→復元保存。既存成果物を無効化し再ビルド |

Web・CLI両方から固定アプリIDと操作だけを管理入口に渡す。Webに任意パス、コマンド、make変数、unit名を指定させない。現行flockはcheckoutごとに置かれるため、複数cloneが同一SDKを使う将来構成では機体/SDK全体の共有ロックが必要。停止操作はビルドや実行ロックの待ち行列に入れず、安全監視に即時届く別経路にする。

当面は名前指定の`start-robot <name>`を正式CLI候補とし、直接makeと名前なしstartを通常教材から外す。最終的には同じsystemd管理経路をCLIにも提供して、CLI開始もWebで観測・停止できるようにする。現行スクリプトだけでこの管理統一が完成しているとは扱わない。直接makeは教員が全サービス停止・機体占有を確認した診断用途へ限定する。

## 4. ビルド・実行物の契約

保存revisionを固定したsnapshotからビルドする。編集中にビルド入力が変化しないよう、体験ではビルド中保存を止めるか、ジョブ開始時のsnapshotを別途固定する。前者を初期試作の標準にする。ファイル全体を再構成し、安全処理のある関数外枠は変更させない。

成果物metadataにはアプリ、作業領域ID、ソースdigest、SDK commit/submodule/dirty識別、toolchain識別、ビルド結果、asp digestを記録する。キャッシュはこの契約へ段階移行し、現行v1を完全な版保証としない。壊れたエントリや必要情報欠落は再ビルド扱いにする。検証済みキャッシュだけを使用し、失敗時に古いaspへフォールバックしない。

実行は「選択した保存revision = ビルド成功revision = 選択成果物」の照合後に行う。最後に保存/復元して以降のビルドがなければ実行不可。共通workspace/aspへの配置から起動まで同じ占有内で行う。Gitのブランチ切替・テンプレート復元は実行中に行わない。展示では教員が全アプリのキャッシュを事前に準備し、開始時の同一性確認を残す。新たな事前ビルド専用配布システムは当初不要。

## 5. 接続方式の推奨

**短時間体験の初回導入は一組一台のPC–Pi有線LANを標準、無線運用が必要な場合の予備は機体AP。** ケーブルは車輪浮上の編集/ビルド時に使用し、走行では引掛かりを防ぐ配置・走行範囲を設計する。ケーブルを外して走らせるならAPへ接続し直して安全leaseを取得してから明示開始する。走行中の切替や無接続走行を前提にしない。

| 接続 | 安定性・多台数 | 接続断と復旧 | 採否 |
| --- | --- | --- | --- |
| PC–Pi有線LAN | 電波干渉なし。直結なら組ごとに独立。PC側USB-LAN等が必要 | ケーブル断。固定IPで再接続。ケーブルによる機体転倒を対策 | 初回体験の標準 |
| 機体AP | 学内認証に依存せず単独完結。多APでチャネル干渉、PCのSSID取り違え | iotNNと筐体IDを照合して再接続、固定URLで状態再取得 | 無線の予備/現地評価後の選択肢 |
| 校内Wi-Fi | 既存設備を使えるが電波、端末隔離、DHCP、認証、AP切替に依存 | IP変更・到達性を教員が確認。有線に退避 | 管理者と到達性/同時台数を確認するまで体験標準にしない |
| 専用の外部AP＋Pi有線スイッチ | 多台数で無線チャネルを集中管理できるが追加設備が必要 | AP故障が共通障害。IP対応表と有線予備 | 台数増加で有線直結が不便になった時の次候補 |
| Pi直結画面/キーボード | 通信に依存しないが機材と設置面積が必要 | ローカル保存済みコードから再開 | 講師用復旧席として有用 |

Pi4のUSB端子にケーブルを挿せば通常のUSB gadget LANになるとは仮定しない。USB Ethernetアダプターとgadget方式は区別する。

ID NNの有線Pi側は現行設計で`192.168.50.(100+NN)/24`。直結PCに同一/24の重複しないアドレス（例`.1`、gatewayなし）を教員が設定する案とする。既存VPN/LANとの経路重複、PCのWi-Fi同時接続、スイッチ集約時のIP重複を事前確認する。機体AP群は同じ192.168.60.0/24を使う別ネットワークなので、単純にブリッジしてまとめない。今回はネットワーク設定を一切変更しない。

SSHとWebはどちらもIP到達性に依存し、Webへ変えるだけでは無線は安定しない。SSH前景プロセスは切断時のSIGHUP・sudo/makeのプロセス関係に左右されるため、停止を保証せず、再接続して状態確認する。Webは保存ACK後のPi上ジョブを接続と分離できる点が便利。保存ACK前は保存できたと断定しない。

## 6. 障害時の安全と継続

保存済みコードとビルドは通信断でもPiに残し、走行許可は期限付きとする。Web体験では所有ブラウザが専用heartbeatを送り、Pi上の独立監視が期限切れ・最大走行時間で停止を要求する。単なる状態GETを走行許可にしない。期限は仮値としてheartbeat 0.5秒・失効2秒を評価開始点にし、停止遅延と走行距離を実測してコースに合わせて決める。バックグラウンドタブの遅延でも安全側に停止する。

切断・再読込・Web再起動で保存とビルドを失わず再取得できる一方、走行は停止側にし、自動再開しない。Pi再起動時も実行ジョブを復活させない。`SIGKILL`でプロセスが消えたことをモーター停止と同一視しない。既存pause/PWM制限を残し、無限ループ・子プロセス・Piハングにも備える安全監視、走行上限、手元の物理停止方法を実機で検証する。停止保証が成立しなければWebから任意編集結果を走らせる段階へ進めない。

通常開発でも教員が停止確認と単独占有を行い、通信断時に継続走行させない監視を共通化する。展示ではブラウザ所有leaseだけに頼らず教員の監督下で最大走行時間と実機停止手段を持つ。安全停止の詳細実装は別PRとし、本提案の承認だけで運用条件を緩和しない。
