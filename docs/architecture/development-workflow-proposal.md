# 推奨する開発・実行方式

未実装の設計提案。[現状](current-state.md)と[不整合](inconsistencies.md)を前提とする。第2回オープンキャンパスは、学生スタッフが参加者にマンツーマンで付き機体横で監督する条件に更新した。今回のPRは設計文書のみ。

## 1. 推奨構成

**正本は各Git checkoutのrobot/、SDK workspaceはビルド・実行専用。通常開発はRemote SSH、短時間体験はtracer_task()本文を通常Cで編集するWeb画面、展示は既存ダッシュボードを使う。** Web/CLIの実行管理入口は共通化する方針を維持する。

SDKや既存make img、キャッシュ、flock、systemdを活かす。汎用Web IDEや独自限定文法AST、一般公開用の任意C実行基盤を初期版には導入しない。機体APへのPC直接接続を第一候補とし、保存・ビルド・実行はPi側で完結してSSH常時接続を不要にする。

外部robot/を参照するmake img経路は既に実装されており、正本統一を妨げる制約は確認できない。ただし採用SDKの依存関係追跡、workspace/appdirの型、HOME固定パス、共通aspによる直列化、実行権限は確認が必要。SDK内でソース編集する方式には戻さない。

## 2. 利用者と作業領域

| 場面 | 編集・保存場所 | 操作 | Gitと復元 |
| --- | --- | --- | --- |
| A 通常開発 | 学生用checkoutのrobot/ | VS Code Remote SSHを標準、nanoは代替。共通管理入口からビルド/実行/終了 | studentブランチ、commit→bundle→PCでverify |
| B 第2回40分体験 | 体験専用cloneのrobot/ocan2026/app.c | 本文編集→保存→ビルド→Web実行で待機→機体ボタンで走行/一時停止。スタッフが常時監督 | 体験用ブランチ。スタッフ専用Restoreで初期本文へ戻す |
| C 展示 | 教員が確定した配布checkout | 既存カードで選択・実行・停止、状態/ログ確認。コード編集なし | commitと成果物を固定、開始前に準備 |

同じ機体でA/B/Cを同時使用しない。教員が実行終了と停止を確認して対象checkoutを切り替える。配布checkoutはWebから書込み不可とし、体験者へGitHub書込み資格情報やGit操作APIを渡さない。ブランチ名だけをmain保護と考えず、保存先と権限を分ける。

本文以外の固定コード、SDK、ヘッダ、Makefile、unitはスタッフ管理とする。体験中は自由な通常C構文を使え、コンパイルエラーを原文表示する。本文境界のサーバー検証と通常Cの構文検査は区別する。詳細は[Web編集検討](web-editor-feasibility.md)を正本とする。

## 3. 各処理の責任

| 処理 | 担当 | 成功条件 |
| --- | --- | --- |
| 編集 | 通常エディタ／体験Web | 体験はtracer_task()本文のみ。独自限定文法を要求しない |
| 保存 | 非特権保存API | 固定範囲・版照合、atomic保存、保存revision応答。他ファイル・mainを変更しない |
| ビルド | 非特権workerと既存build機構 | 保存版を固定、固定argv、終了コードとコンパイラ原文ログ、成果物識別 |
| Web実行 | 実行管理＋systemd | 対応成果物を単独起動し、待機状態でモーター停止。走行を始めない |
| 機体の走行／一時停止 | 固定のボタン監視と出力許可ゲート | 押すたびに開始→一時停止→再開。通信・学習本文から独立 |
| Web実行終了 | 実行管理 | モーター停止とプログラム終了を確認。ビルドロック待ちにしない |
| Restore | スタッフ専用API | 実行終了→初期本文復元→旧成果物無効化。自動起動・走行なし |

機体ボタンは開始時の一回待ちだけでは不足する。押下エッジと解放をチャタリング対策付きで検出する。起動時押しっぱなし・長押しでは走行開始/反復切替せず、解放後の新押下を必要とする。待機/一時停止とプログラム終了を表示上も分ける。

固定監視タスクを学習処理より優先し、pause中はモーター出力層で再駆動を抑止する設計を優先する。本文の周期処理が返ることに停止を依存させない。無限ループ・長い待ちでも停止できるか、SDKのスケジューラ、タスク中断、周期起動、出力APIの組合せを実機で確認する。OSやハード停止時の物理停止方法も確認する。ソフトウェアボタンが全故障を止められるとは保証しない。

## 4. 管理入口・成果物・権限

固定アプリIDと操作だけをWeb/CLIから共通管理入口へ渡す。任意パス、unit名、コマンド、make変数の入力機能は提供しない。複数cloneが同じSDKを使うならcheckout単位の現行flockでは不足するため、SDK/機体全体の占有が必要。初期体験では一台一組・選択済み体験cloneのみで開始し、共通入口の全面再設計を体験に不要な範囲まで広げない。

名前指定start-robotを既存の入口候補として活かすが、ocan2026が起動直後に待機してボタン切替できるようにする変更は別実装PRで必要。名前なし既存asp起動と直接makeを通常教材から外す。最終的にはCLI起動もWebで観測・終了できるようにする。

保存revisionを固定してビルドし、「保存版＝ビルド成功版＝起動成果物」を確認する。初期版は実行終了後だけ保存/ビルド可能とし、ビルド中の保存も止める。失敗後に古いaspへフォールバックしない。Restoreや保存後は旧成果物を実行不可にする。共通workspace/aspへの配置から起動まで占有を維持する。

成果物metadataはsource digest、SDK/toolchain識別、ビルド成否、asp digestを段階的に整える。第2回の最小版でまず必要なのは対象保存版と成功成果物の対応、失敗版・古い版の起動拒否、二重起動防止。全アプリのcache形式刷新や旧unit依存整理は後続作業に分けられる。

Web・保存・ビルドには不要な管理者権限を与えず、実行はSDKで必要な最小権限だけを固定入口へ委譲する。通常Cを許す以上、本文制限だけでCからのOS操作まで隔離できるとはしない。実行時権限を調査し、スタッフが内容を確認する体験専用機能とする。既存sudoersの拡大やrootでのユーザー編集Makefile実行を前提にしない。

## 5. ネットワークの推奨

**機体APへのPC直接接続を第一候補とする。** SSIDはiotNN、接続プロファイル名はraspike-ap。筐体IDとURLを照合し、会場で予定台数を同時接続して安定性を評価する。Web編集はPi側ジョブ管理によりSSH常時接続を不要にするが、無線品質そのものを改善するわけではない。

| 方式 | 採用条件・役割 | 復旧・注意 |
| --- | --- | --- |
| 機体APへ直接接続 | 第2回の第一候補。学内認証に依存せず各機体で完結 | 多APの干渉、SSID誤選択、PCの自動切替を検証。固定URLで再取得 |
| 有線LAN | AP多台数試験で不安定な場合の代替 | PC側IP/USB-LAN等を準備。ケーブル引掛かりを避けて走行範囲を限定 |
| HDMI＋ローカル画面・キーボード/マウス | 無線/有線接続が困難な時の代替、復旧席 | HDMIだけではコード入力できない。Pi上のブラウザから同じ画面を使えるよう準備 |
| 校内Wi-Fi | 管理者と到達性・端末隔離・認証を確認できた場合の補助 | DHCP/IP変更と学内運用に依存。第2回の第一候補にしない |
| 専用外部AP＋有線スイッチ | 将来の多台数集約案 | 初期版の必須設備にはしない |

現行設計のPi側APアドレスは192.168.60.(100+NN)/24、有線は192.168.50.(100+NN)/24。有線に切り替える場合はPC側の重複しないアドレスと経路をスタッフが確認する。別APの同一サブネットを安易にブリッジしない。Pi4のUSB接続をgadget LANと仮定しない。今回は実機ネットワーク設定を変更しない。

## 6. 通信断と授業継続

PC・ブラウザとPi間のWi-Fi断ではロボットを自動停止させない。ブラウザHeartbeatやlease失効を走行停止条件にせず、常時接続を走行の前提にしない。保存ACK後のコード・ビルドジョブはPiで保持/継続し、実行もブラウザやSSHの接続寿命から切り離す。正常起動後はブラウザ再読込・タブ閉じ・Wi-Fi断・Webプロセス再起動と独立してプログラムを継続する。走行中はそのまま走行を継続し、復帰時は現在状態を取得するだけでプログラムを自動再起動しない。

その前提として機体ボタンの一時停止は通信状態と独立して動き、機体横のスタッフが停止できることを必須とする。接続回復後は保存revision、ジョブ結果、機体状態を再取得し、実行や走行再開を自動要求しない。待機中/一時停止中なら切断だけで走行へ遷移せず、ボタン押下でのみ開始/再開する。

Web実行終了はネットワーク到達時の終了手段で、断線中の代替にはならない。SSH切断時の前景プロセス挙動も停止保証に使わない。Pi再起動後は自動走行させない。既存アプリのPWM制限・pause・通信失敗時停止を維持する。Pi内部のカメラ画像/制御指令の更新停止とPython–C通信断での安全停止も維持すべき要件であり、ブラウザ通信とは別のローカル監視で扱う。静的調査で期限・鮮度判定に未確認/不足があるため、内部停止機能がすべて実装済みと断定せず、実機で確かめ不足は別PRで補う。カメラ/Pythonを使わないocan2026にそれらの接続を要求しない。

## 7. スタッフ専用Restoreと導入判断

Restoreは実行終了と停止確認後、体験用本文を初期状態へ復元し新revisionにする。mainや固定コードを変更せず、旧ビルド結果を無効化する。必要なら再ビルドするが、復元後に自動起動・走行しない。次のWeb実行は待機のみで、機体の新しいボタン押下が必要。スタッフ権限はサーバーで検査する。

第2回の導入条件は、機体ボタンの通常/制御異常/通信断での停止、チャタリング対策、Web実行終了、Restore、版対応と権限の確認、多台数AP試験と代替接続準備を満たすこと。通常開発の全面統一や一般公開用の安全基盤をすべて完成させるまで待つ計画にはしない。今回は設計レビューに留め、実装開始・mainマージを行わない。
