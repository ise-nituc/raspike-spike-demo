# 第2回オープンキャンパス：学生スタッフ用 実機確認ガイダンス（準備版）

> **重要**：この文書は学生が現場で確認・報告するための手順です。機体ボタンの「開始→一時停止→再開」機能は現状未実装です。実装済みとみなして走行させないでください。
>
> 担当教員は遠隔でレビューします。判断できない点があれば**操作を止めて記録・報告**してください。既存ソースを上書きしたり、ネットワークやOS設定を変更したりして解決しないでください。

## 目的・担当分担

- **学生スタッフ（現地）**：機体番号と状態の確認、既存動作の観察、安全な範囲での実機検証、記録・報告。
- **Codex／開発担当**：変更案の実装、コードレビュー用のDraft PR、可能な範囲の自動テスト。
- **担当教員（遠隔）**：報告の確認、次段階へ進む判断、実機試験の承認。
- **必ず2名で初回走行を確認**：1名が操作し、もう1名がロボットと走行範囲を監視。単独・無監督で新しいプログラムを走らせない。

第1回教材は `robot/ocan2026/` に対応する。参加者に編集させる予定の領域は `app.c` の `tracer_task()` 本文のみ。

## 0. 作業前の連絡・準備

1. 教員に機体番号（例：IoT04）、作業日時、学生担当者、使用するPCを連絡する。
2. ロボットを安定した台に置き、**車輪が床・机に接触しないようにする**。周囲に人や物が触れないことを確認する。
3. SPIKE Primeの物理的な電源停止方法を確認する。フォースセンサーはソフトウェア入力なので、ソフトが固まったときの確実な電源停止方法とは区別する。
4. 予備の停止担当を決める。走行中に異常を感じたら直ちに停止し、確認できるまで再開しない。
5. ネットワーク不調だけを理由にロボットが停止する仕様にはしない。Webの「停止」は接続断中に利用できないため、現場では機体側の停止手段を優先する。

## 1. 変更せずに現状を記録する（読み取りのみ）

Raspberry Piのターミナルで以下を実行し、出力を保存する。

```bash
hostname
cat /etc/raspike-id
cd ~/raspike-spike-demo
git status -sb
git branch --show-current
git log -1 --oneline
git remote -v
ls -ld ~/RasPike-ART/sdk/workspace
ls -l ~/RasPike-ART/sdk/workspace/appdir ~/RasPike-ART/sdk/workspace/asp 2>&1
```

- `git status` に変更がある場合は、その状態を**消さず**報告する。
- `git pull`、`git restore`、`git reset --hard`、`sudo`、`make start`、`scripts/setup` は、この確認段階では実行しない。
- 現地にある旧版の `app.c` 等がGitHub版と異なる可能性がある。差分は教員と確認するまで保持する。

## 2. 既存プログラムの構造を確認する（編集しない）

以下のファイルを開いて、該当箇所を確認する。

- `robot/ocan2026/app.c`：`main_task()` はフォースセンサーの初回押下を待つ。 `tracer_task()` が参加者の編集箇所。
- `robot/ocan2026/LineTracer/LineTracer.c`：`forward/left/right/stop` がモーター出力を設定する。
- `robot/ocan2026/app.cfg` と `app.h`：タスクと周期の定義。

**現状では押すたびに一時停止・再開する仕様ではありません**。その動作を期待して現行バイナリを走らせないでください。

確認する事項：
- フォースセンサー、カラーセンサー、モーターの実機ポート
- 操作ボタンと電源停止方法
- 初期状態のソースと既存デモのバージョン
- 機体に搭載されたSDKのパスとバージョン

## 3. 新しい機体ボタン機能の実機検証（実装PRレビュー・教員承認後のみ）

**この節は実装済みの最新版と、教員の実機試験許可を受けたときだけ実施する。** 初期状態では実施しない。

1. 対象のPR、コミット、変更ファイルを確認し、既存の変更を保存したうえで所定の検証環境を使用する。
2. 学生が使う `robot/ocan2026/app.c` の本文は、まず `forward();` だけにする。低速の安全な設定とし、最初は車輪を浮かせる。
3. 教員が指定した手順でビルドする。**ビルド成功が確認できない場合は実行しない**。古い `asp` の存在を成功とみなさない。
4. プログラム起動直後は、車輪が**止まっている**ことを確認する。
5. フォースセンサーを一度押し、車輪が回ることを確認する。
6. もう一度押すと車輪が停止し、停止中に再び回り始めないことを確認する。
7. もう一度押すと再開することを確認する。
8. 長押し、素早い連打、起動時押しっぱなしでも意図しない反復切替・自動走行が起こらないことを確認する。
9. Wi-Fiを一時的に切断しても、機体側ボタンによる停止が機能することを確認する。**切断中のWeb停止に頼らない**。
10. まず車輪を浮かせた状態で全項目に合格した後、教員の追加承認と安全なコース確保を経て、低速の床面走行を確認する。

**異常時はただちに試験を中止する。** 停止ボタンを押しても車輪が回り続ける、停止後に勝手に再駆動する、誤ったバイナリが動く、異常な発熱・電圧低下がある場合は、物理的な停止手段で安全を確保し、以後の走行を行わない。

無限ループや異常コードによる試験は、通常動作の確認後に別途手順・環境を定めて実施する。現地学生が独自に危険な試験コードを作成しない。

## 5. 第2回OC向けの運用条件（参考）

- 本番ではWebの「実行」は**起動・待機**のみ。機体のフォースセンサーで走行開始／一時停止／再開を切り替える。
- ブラウザ表示が止まってもPi内部の制御が正常なら走行継続する。ただし機体側の停止操作はいつでも有効にする。
- 参加者交代時はスタッフが**実行終了・停止確認 → Restore → 必要なら再ビルド**する。Gitの破壊的操作を参加者に実行させない。
- コースや通信が不安定な場合は、検証済みデモやHDMI接続による代替手順に戻す。

## 6. 教員が遠隔で判断するポイント

1. 既存機体の未保存変更がないか。
2. ボタン監視とモーター停止が学生編集コードから独立しているか。
3. 新版をビルドした証拠があるか（失敗時に旧版を実行していないか）。
4. 停止・再開・Wi-Fi断の結果を学生が記録したか。
5. 初回の車輪浮上試験が合格したか。**床面走行は別判断**とする。
